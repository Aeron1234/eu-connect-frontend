# DTR location assignment manual and handoff

Supervisor schedule dates now preselect working days: both endpoints count, ranges shorter than seven days select only the covered weekdays, and longer ranges select all seven. Uncheck rest days as needed. Open-ended periods use manual day selection. Existing saved schedules stay unchanged until saved. Search placeholders and student/location/count separators use plain punctuation after correcting garbled source text. No backend/schema/configuration change is required.

Open **DTR Restrictions** from the sidebar, or `/dtr-restrictions` directly. Old `/dtr-locations` links redirect here. The page manual and `/help` cards use `components/help-ui/guides/bulkDtrGuide.js` as the shared role-aware source.

## Who can use it

- Admin: all ongoing internships; Departments and dependent Courses filters.
- Department head: ongoing interns within their current department; Courses filter. Registrar heads are excluded from navigation, Help/manuals, the page and API.
- Employer: only their supervised ongoing internships; name search, without school-wide department/course filters.
- Students have no access to this management page. Their location remains available through their existing dashboard attendance tools and notifications.

## Individual and bulk workflow

1. Search by student name and use available filters. Table rows show avatars, names, course, department where applicable, company and current assignment. A student without a custom override uses the saved company location with a 150 m default, or shows no location if company coordinates are missing.
2. Tick one student for an individual assignment or several for bulk. The header checkbox selects **only the current page**, never every matching page. There are ten internship rows per page and a maximum of 100 per save. Selections persist across pages and filters; check the collective panel to review/remove individuals or Clear all. Hidden selections are still included in the reviewed action.
3. Search in the map (the existing one-second geocoder delay/loading remains) or click the desired point. Alternatively, ask one student to tap **Share location** on their dashboard, then choose **Live pin** beside that student in the table or selected list. Only one student's temporary position is watched at a time. Its blue pin and accuracy circle disappear when sharing stops or expires. **Use student's pin** copies the coordinates into the maroon draft for all selected students; it never saves or moves an existing assignment automatically. Confirm/edit the address, keep it and any note within 255 characters, and choose a whole-number radius from 20-2,000 m. The default is 150 m. Coordinates alone are valid; notices use them if no address is supplied.
4. Select **Review assignment**. The confirmation records the selected IDs, location and radius so background map lookups cannot alter what is saved. Saving replaces existing assignments and creates overrides for company-default students. It does not change company addresses, old attendance, hours or internship dates.
5. Read the result counts. Successful and unchanged selections are cleared; failures remain selected with student names and reasons. Refresh updates both table and map. Unchanged assignments send no duplicate notices. When a request cannot be confirmed, refresh before retrying: it may have committed already. Unexpected database errors roll back the write set; inaccessible/stale internships are reported individually while eligible records can succeed.

Blue map pins group **effective DTR locations at the same coordinates** across authorized students in the current search/filters, across all table pages. Open a pin to see count, avatars, names, notes and per-student radius. Different locations have different pins; a single student also has a pin. Reassignment moves membership after refresh. Pins never reveal students outside the viewer's permissions. Company fallback locations are included in pins and labeled as company defaults.

The temporary live pin is separate from those saved group pins. Watching does not add the student to the assignment selection. Before using the shared pin for a bulk save, check the selected-student panel: the copied position will be assigned to everyone selected, including students hidden by the current filter. If the reported GPS accuracy is larger than the allowed DTR radius, verify the physical location before confirming. Stop watching to release the live subscription; the student's own Stop sharing control or leaving their dashboard also clears the temporary position.

Every changed student receives a notification identifying the assigned/updated location and instructing them to remain inside the radius for clock-in and clock-out. Existing attendance/start-date rules continue. Admin/head actions also notify assigned supervising employers, grouped once per employer per action with student names, location and the setter's name. Students without supervisors still get their own notice. Employer actions notify changed students but do not create employer self-notifications.

## Implementation and setup

The backend owns fresh authorization, latest academic membership, supervisor relationships, validation, row locking, upserts and transactional notification persistence. Frontend role guards and viewer-scoped query keys support the UI, not API authorization. Selection uses internship IDs held only in this page's memory, reset when viewer identity changes. The existing profile editor and bulk endpoint share backend validation; both write `dtr_locations`. The bulk page reuses the individual editor's Socket.IO live-location watch and map marker; the backend authorizes each watched student/internship, including the Registrar exclusion. Live coordinates are temporary and separate from the saved geofence and attendance entries. The existing map form accepts optional Leaflet children for saved pins, leaving other map forms intact. No new routing/geocoding service or key is introduced.

API reads: `/api/v1/dtr-restrictions/students` and `/pins`; write: `/assign`. Browser server actions retain HttpOnly token handling, private/no-store reads and bounded waits; no automatic write retries. Loading skeletons cover route/table/map import; errors have retry, and access-denied results hide cached records/pins. Saved notices and manual refresh remain useful when sockets disconnect.

The original location assignment workflow needs no new SQL structures. Run backend `scripts/2026-10-30-bulk-dtr-locations.sql` to verify the existing InnoDB tables, coordinate types, one-per-internship unique index, foreign keys and `dtr_location_set` notification fields. The employer shift-hours feature needs `scripts/2026-11-05-dtr-shift-restrictions.sql`; apply it after `scripts/2026-11-05-dtr-attendance-photos.sql` and before deploying the schedule-aware backend. Deploy the matching frontend afterward. No `.env` or package changes are required. Backend details: `../ims-backend/features/dtr-locations/README.md` in the paired checkout.

## Employer shift hours

The employer may enter an optional start date, end date, or both for each student's expected hours. Dates are inclusive; blank dates are unbounded. Existing schedules remain unbounded after the migration. The schedule applies by shift start date, so overnight work beginning on the final date retains its expected clock-out the next morning. Saved dates appear in the employer table and editor. Schedule set/update/remove actions notify the student and create an activity log; identical saves do not. Apply backend `scripts/2026-11-06-dtr-shift-date-range-notifications.sql` after the initial shift migration and before deploying the matching backend and frontend.

Employers alone can set, edit or remove expected daily clock-in and clock-out times beside a currently supervised ongoing intern. The backend rechecks the employer/internship relationship and active status for every write. A clock-out time before the start time defines an overnight shift; the times use Philippine time. Existing DTR entries keep their original labels when the schedule changes. At clock-in, the current schedule is copied to that DTR entry. The entry is Late at 10 minutes or more after the expected start; a manual clock-out before the expected end is Undertime, and 30 minutes or more after it is Overtime. These labels appear in shared DTR tables and do not prevent attendance or change credited hours. Without a schedule, no timing label is set.
